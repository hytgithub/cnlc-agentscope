# 测井解释智能体项目上下文

## 1. 项目概述

本项目基于 **AgentScope** 构建一套面向常规测井解释业务的智能体系统。

系统主要服务于 **测井解释工程师**，目标是将测井解释业务流程、专业计算工具、结构化数据、大语言模型推理能力以及多源资料验证能力组合起来，形成一套可执行、可追踪、可扩展的测井解释 Agent 系统。

本项目不是简单实现：

```text
测井数据
→
大模型
→
解释报告
```

而是按照真实测井解释业务流程执行：

```text
原始资料
→
数据检查
→
数据处理
→
专业参数计算
→
阶段性解释
→
综合判断
→
多源资料验证
→
最终解释结论
→
单井测井解释报告
```

系统应尽可能保留解释过程中的数据来源、中间结果、工具调用、判断依据以及异常信息，使测井解释过程能够被追踪和复核。

## 2. 项目目标

### 2.1 总体目标

构建一套能够辅助测井解释工程师完成单井常规测井解释工作的智能体系统。

系统未来应能够：

1. 接收井基本资料和测井相关数据；
2. 检查输入数据完整性；
3. 执行测井数据预处理和质量控制；
4. 调用专业算法计算中间解释参数；
5. 完成岩性识别；
6. 完成储层识别及物性评价；
7. 完成流体识别；
8. 完成油、气、水层分类；
9. 完成层段划分及有效厚度计算；
10. 综合岩心、录井、试油、邻井等资料进行验证；
11. 对冲突、缺失和异常信息进行标记；
12. 最终生成结构化测井解释结果及单井解释报告。

## 3. 最终用户

系统主要用户为：

> **测井解释工程师**

系统定位是：

> 测井解释辅助系统，而不是完全替代测井解释工程师的黑盒自动解释系统。

系统需要能够向专业人员展示：

- 使用了什么数据；
- 计算了什么参数；
- 调用了哪些工具；
- 得出了什么阶段性结论；
- 最终结论依据是什么；
- 是否存在数据冲突；
- 是否存在重要数据缺失；
- 是否需要人工复核。

## 4. 核心业务流程

当前确认的测井解释业务主流程为：

```text
原始资料准备
↓
数据预处理与质量控制
↓
岩性识别
↓
储层识别与物性评价
↓

↓

↓

↓
岩心 / 录井 / 试油 / 邻井综合验证
↓
形成单井测井解释报告
```

在系统实现过程中，该流程进一步抽象为：

```text
W01 任务初始化与原始资料加载
↓
W02 数据完整性检查
↓
W03 数据预处理与质量控制
↓
W04 岩性识别
↓

↓
W06 流体识别
↓

↓
W08 层段划分与有效厚度计算
↓
W09 多源资料综合验证
↓
W10 最终一致性检查与报告生成
```

详细 Workflow 定义由 `01-business-workflow.md` 描述。

## 5. 核心设计原则

### 5.1 Agent 负责决策

Agent 主要负责：

- 任务理解；
- 任务规划；
- 综合分析；
- 动态决策；
- Tool 选择；
- 多源证据综合；
- 冲突处理；
- 异常情况下的下一步判断。

### 5.2 Tool 负责执行

具有明确输入、确定执行逻辑和明确输出的能力，优先实现为 Tool。

例如：

```text
读取井数据
读取测井曲线
Vsh 计算
孔隙度计算
渗透率计算
Sw 计算
数据质量检查
层段合并
有效厚度计算
```

Agent 原则上不直接完成这些确定性计算。

### 5.3 Workflow 负责流程控制

Workflow 负责：

- 业务步骤编排；
- 状态流转；
- 前置条件检查；
- 成功 / 失败分支；
- 重试；
- 回退；
- 人工复核分支。

业务步骤不等于 Agent。

### 5.4 LLM 不替代专业算法

对于已有明确公式、程序或专业算法的问题，应优先调用专业 Tool。

例如：

```text
DEN / CNL / AC
→
孔隙度计算 Tool
→
Porosity
```

不允许直接要求 LLM 根据输入数据猜测孔隙度。

### 5.5 不允许编造业务数据

系统不得：

- 编造原始测井数据；
- 编造录井资料；
- 编造岩心资料；
- 编造试油资料；
- 编造邻井资料；
- 编造专业计算结果。

当输入资料不足时，应明确标记：

```text
Missing Data
Warning
Blocked
Review Required
```

而不是补造数据。

### 6.2 原始测井资料

- CNL；
- AC；
- RT；
- RXO；
- CAL；
- 其他常规测井曲线。

### 6.3 辅助资料

包括：

- 岩心资料；
- 录井资料；
- 试油资料；
- 邻井资料；
- 地质资料。

### 6.4 专业知识

未来可以接入：

- 区块解释标准；

## 7. 系统主要输出

系统输出分为三个层次。

### 7.1 中间计算结果

例如：

```text
Vsh
Porosity
Permeability
Sw
相关电阻率分析结果
其他专业参数
```

### 7.2 阶段解释结果

包括：

- 数据 QC 结果；
- 岩性识别结果；
- 储层识别结果；
- 储层物性评价；
- 流体识别结果；
- 油气水层分类结果；
- 层段划分结果；
- 有效厚度计算结果；
- 多源资料验证结果。

### 7.3 最终结果

第一阶段最终输出格式：

#### JSON

用于：

- 系统之间的数据交互；
- 状态保存；
- 后续程序处理；
- 自动化测试。

#### Markdown

用于：

- 测井解释工程师阅读；
- 调试；
- 演示；
- 后续转正式报告。

第一阶段暂不要求生成 Word 或 PDF 报告。

## 8. 模型接入

项目使用：

> **内部统一大模型**

系统不直接将具体模型调用散落在 Agent 和业务代码中。

应设计统一的模型访问层：

```text
Agent
↓
Model Interface
↓
Internal Model Adapter
↓
内部统一模型
```

未来更换模型时，应尽量不修改上层 Agent 业务逻辑。

主模型主要负责：

- 任务规划；
- 复杂推理；
- 多信息综合；
- 重要解释决策。

未来允许针对简单任务接入轻量模型，但第一阶段不作为必须能力。

## 9. Agent Framework

项目 Agent Framework 使用：

> **AgentScope**

AgentScope 主要用于承载：

- Agent；
- Agent 调用；
- Tool 调用；
- 上下文交互；
- Workflow 协作；
- 基础 Agent 运行能力。

项目业务逻辑不应过度绑定框架内部实现。

在关键业务模块之间仍应通过明确 Interface 和 Domain Model 进行隔离。

## 10. 第一阶段 Agent 架构方向

当前 V0.1 优先采用精简多 Agent 设计。

初步包含：

```text
MainAgent
InterpretationAgent
ValidationAgent
```

### 10.1 MainAgent

主要负责：

```text
任务理解
↓
任务规划
↓
Workflow 启动
↓
专业 Agent 调度
↓
状态检查
↓
异常处理
↓
最终结果汇总
```

MainAgent 不直接负责确定性测井计算。

### 10.2 InterpretationAgent

主要负责：

- 流体综合识别；
- 油气水层分类；
- 多参数综合推理；
- 根据解释需求选择专业 Tool；
- 补充解释证据。

### 10.3 ValidationAgent

主要负责：

- 对解释结果进行独立检查；
- 综合岩心资料；
- 综合录井资料；
- 综合试油资料；
- 综合邻井资料；
- 发现解释结果与实际资料的冲突；
- 提出重新解释或人工复核建议。

具体 Agent 边界由 `02-agent-tool-boundary.md` 进一步定义。

## 11. 统一状态管理

整个单井解释任务应围绕统一状态对象运行：

```text
InterpretationState
```

至少需要能够承载：

```text
task
well
raw_data
processed_data
qc_result
lithology_result
petrophysics_result
fluid_result
layer_classification
interval_result
validation_result
missing_data
warnings
errors
current_step
completed_steps
review_required
```

具体 Schema 后续单独设计。

## 12. 数据库

第一阶段：

> **真实接入数据库。**

数据库主要用于保存需要长期持久化的数据。

候选包括：

- Task；
- Well 基础信息；
- InterpretationState 关键结果；
- 解释结果；
- Report；
- Workflow 执行记录；
- Agent 执行记录。

具体数据库类型及 ORM 技术在技术架构阶段确定。

## 13. Redis

第一阶段：

> **真实接入 Redis。**

Redis 主要用于承担运行时、高频或短生命周期状态能力。

候选职责包括：

- 运行中的 Task State；
- Workflow 临时状态；
- Agent Session；
- Cache；
- 分布式锁；
- 横向扩展时的共享状态。

Redis 与数据库的最终职责边界将在总体技术架构阶段确定。

## 14. Web 交互

第一阶段需要：

> **简单 Web 页面。**

优先使用 AgentScope 当前项目能力或与 AgentScope 配套的简单交互方式完成演示和调试。

第一阶段 Web 页面主要服务于：

- 提交解释任务；
- 输入或选择测试井数据；
- 查看 Agent 执行过程；
- 查看 Workflow 状态；
- 查看最终 JSON；
- 查看 Markdown 报告。

第一阶段不以建设完整生产级前端系统为目标。

## 15. 测试数据

第一阶段由项目方提供测试数据。

这些数据作为：

> Mock / Test Well Data

用于系统开发和端到端测试。

当前：

> **具体测试数据格式尚未最终确定。**

后续需要结合实际测试数据定义正式 Schema。

数据格式设计时应优先满足：

- 结构清晰；
- 字段含义明确；
- 支持缺失字段；
- 支持扩展；
- 支持单井完整数据；
- 支持各 Workflow 节点读取；
- 支持 JSON 序列化；
- 支持自动测试。

该事项属于后续需要解决的开放问题。

## 18. 第一阶段不追求的目标

V0.1 暂不以以下内容作为主要目标：

- 所有专业测井算法全部真实实现；
- 达到生产级测井解释准确率；
- 建设完整复杂前端；
- 建设完整权限系统；
- 建设 Kubernetes 高可用集群；
- 完整性能容量规划；
- 完整 CI/CD 平台；
- 完整企业级安全体系。

第一阶段优先验证：

> 当前架构是否能够真正工作。

## 19. 架构扩展目标

虽然第一阶段以跑通为主，但系统架构必须考虑后续扩展。

需要支持：

```text
增加新的专业 Tool
增加新的测井算法
Mock Tool → Real Tool
增加新的专业 Agent
接入轻量模型
更换主模型
接入真实测井数据平台
增加新的解释 Workflow
横向扩展 Agent 服务
```

新增能力原则上不应要求大规模修改已有业务代码。

## 20. 可观测性要求

系统需要记录至少以下调用链：

```text
Task
↓
Workflow Step
↓
Agent
↓
Tool
↓
Tool Result
↓
Agent Result
↓
State Change
↓
Final Result
```

后续需要能够回答：

> 某一个解释结论是怎样得到的？

因此 Trace 是系统核心能力，而不是普通调试日志。

第一阶段采用开源 Trace / Observability 方案，具体产品在总体技术架构阶段确定。

## 21. 当前成功标准

当前项目第一阶段最重要的成功标准是：

> **跑通。**

具体表现为：

1. 测试井可以进入系统；
2. AgentScope Agent 可以正常执行；
3. Workflow 可以完整流转；
4. Agent 可以调用 Tool；
5. InterpretationState 可以持续更新；
6. 数据库正常持久化；
7. Redis 正常参与运行状态管理；
8. InterpretationAgent 能完成 Mock 综合解释；
9. ValidationAgent 能完成 Mock 综合验证；
10. 系统能够处理基础异常；
11. 可以生成最终 JSON；
12. 可以生成最终 Markdown 报告；
13. Web 页面可以看到基本执行和结果；
14. 整条链路可以稳定重复运行。

专业解释准确率将在技术骨架跑通以后逐步提高。

以下事项尚未最终确定，不应由 Codex 自行猜测：

1. 测试井 JSON 的正式 Schema；

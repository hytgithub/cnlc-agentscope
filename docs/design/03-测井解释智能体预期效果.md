# 03｜测井解释智能体预期效果（讨论稿）

> 版本：v0.1  
> 日期：2026-09-30  
> 状态：用户体验与行为预期已讨论；真实业务数值及交互细则待验证  
> 定位：回答“智能体做成以后，用户和评审人员实际应当看到什么”，不预先确定具体界面或底层技术。

对应文档：[01 需求](./01-测井解释智能体需求规格说明.md) ｜ [02 目标](./02-测井解释智能体建设目标.md) ｜ [04 技术方案](./04-测井解释智能体技术方案.md) ｜ [05 测试验收](./05-测井解释智能体测试与验收方案.md)

## 1. 总体预期效果

用户面对的是一个**围绕当前井持续工作的交互式测井解释助手**，而不是固定流程的聊天外壳。用户用业务语言提出要求；系统依据真实业务上下文决定查询、完整解释、修改、重解释、比较、暂停／继续或报告操作；每个正式结果来自可信业务工具，并能追溯来源和版本。

本文件是本轮讨论形成的**设计预期**，不表示各功能已经实现。2026-09-29 会议为四阶段、自然语言修改、阶段确认、上下文保持、Mock 验证和透明化执行过程提供了直接讨论背景；这里列出的完整交互体验、两类视图和示例表达属于后续设计细化。

## 2. E01｜自然语言直接表达业务要求

**用户看到的效果：**

- 不需要输入内部 W01～W10、`task_id` 或 `execution_id` 才能发起业务请求；
- 可以用日常业务语言询问解释结果、要求修改或提出重新解释；
- 用户连续对话时，系统尽可能正确理解已明确的当前井、层段和结果版本；
- 目标对象含糊或操作超出能力边界时，系统会明确说明或询问必要信息，不假装执行成功。

**交互示例（仅用于说明行为，不代表真实井结果）：**

> 用户：帮我解释一下这口井。  
> 用户：看看 2035—2038 m 这一层。  
> 用户：把刚才这层孔隙度改成 0.16。  
> 用户：比较修改前后的结果。

系统应正确区分上述动作，而不是把所有输入送入完整的四阶段流程。

对应目标：G01、G03。

## 3. E02｜新井完整解释清晰展现四阶段

用户发起完整解释时，系统按以下业务主线展示进度：

```text
当前井：示例井 WELL_001（示意）
数据解编      完成
数据预处理    完成
智能处理      执行中
报告生成      未开始
```

每个阶段的展示重点是：

1. 当前在处理什么；
2. 是否完成、有无错误；
3. 获得了什么关键结果；
4. 如需确认，用户下一步可以做什么。

**阶段输出示例（仅示意，必须替换为真实 Tool 返回字段）：**

- 数据解编：实际解出的曲线清单、深度范围、资料缺失／异常提示；
- 数据预处理：质量检查摘要、已执行的校正或处理、待关注问题；
- 智能处理：真实 API 输出的专业结果类别、已完成内容、异常或限制；
- 报告生成：实际生成的报告及其所依赖的结果版本。

不要求向普通用户直接展示完整原始文件或大段底层 JSON；详情及完整日志可供调试和业务复核使用。

四阶段是**完整解释任务的展示结构**，不是查询或比较等所有操作的必经页面。

对应目标：G01、G02。

## 4. E03｜解释完成后可以继续查询和操作

一次完整解释完成后，用户不必重新上传同一井资料，仍可基于已有结果继续：

- 询问某个层段的已有解释结果；
- 查看当前结果所用版本；
- 发起受控修改；
- 申请重新解释；
- 比较明确的新旧结果；
- 在报告策略允许时重新生成报告。

**示例：**

> 用户：2035—2038 m 怎么样？

系统应直接读取该井适当版本的已存解释结果，并明确数据来源；不因为出现“层段”二字就启动整井计算。

如没有该层段结果，应如实说明缺少什么或需要补充哪一步，而不是由模型自行编造砂岩、孔隙度等专业结论。

对应目标：G01、G03。

## 5. E04｜参数修改前先识别与校验

用户提出“修改这一层孔隙度”时，预期的系统行为是：

1. 确定用户想修改的井、层段、基础结果版本、参数及数值；
2. 调用受控的业务工具检查当前是否允许这样修改；
3. 如存在歧义、权限问题、越界或业务规则缺失，暂停修改并作出准确反馈；
4. 通过校验后按规定产生修改记录，保留原有有效数据。

**示意反馈，不是当前已实现界面：**

```text
操作：修改指定层段解释参数
井：以真实业务上下文为准
层段：2035—2038 m（示例）
参数：POR（仅示例，是否允许修改待确认）
目标值：0.16（示例）
状态：待业务规则校验／待确认
```

“把某层孔隙度改成 0.16”究竟修改层均值、采样点还是修正参数，尚需业务确认；系统不能提前将某一种解释写成默认事实。

对应目标：G04。

## 6. E05｜根据真实影响执行重解释并诚实反馈

通过受控修改后，系统依据**已确认的专业依赖及实际第三方 API 能力**确定需要更新的结果。

用户应能够了解：

- 哪些业务结果被认定为受影响；
- 执行了哪些计算或调用；
- 是否按要求只更新相关结果；
- 因真实 API 限制而发生的额外整井处理；
- 是否形成了有效新版本，或为什么尚未生效。

**必须区分：**

| 维度 | 预期效果 |
|---|---|
| 业务结果局部更新 | 仅按真实依赖更新实际受影响的结果，不随意覆盖无关结果 |
| 底层物理局部计算 | 只有第三方 API 经实测支持时才宣称已实现；否则展示实际执行方式 |

例如：如果底层只能整井执行，应如实说明“底层进行了整井计算，本次仅按已确认规则更新指定受影响结果”；不能假装真实计算只运行了某一层。

对应目标：G05。

## 7. E06｜修改前后的结果和来源清晰可追溯

修改、重新解释及报告操作不会静默覆盖旧的有效结果。

用户应能查看：

- 修改前与修改后的明确版本；
- 修改对象、范围及相关记录；
- 两版结果真正发生变化的字段；
- 报告依据的解释结果版本；
- 不可用、失败或尚未完成的结果状态。

**示意：** 版本 V1 已有效；在其基础上发起一次修改生成 V2。仅当必要业务计算与校验全部满足时，V2 才能按规定生效；V1 仍可回看。实际版本格式沿用现有业务系统，不要求采用字面上的 V1/V2 命名。

若专业数据缺失，应在比较表中明确标识，不填充模型猜测的数值。

对应目标：G03、G04。

## 8. E07｜失败时提供真实状态并保留有效结果

真实 API 调用耗时较长或出错时，系统不应只给一个“成功”或“失败”的笼统答案。

期望能区分：

- 已提交、排队、执行中；
- 已完成但结果待校验；
- 校验通过并形成可用结果；
- 已明确失败；
- 请求超时但外部任务实际结果仍未知；
- 用户已停止 Agent 后续操作，但第三方任务可能还在执行。

**关键底线：** 不完整新结果不能被标为正式成功；上一个有效版本仍可用；外部旧任务即使迟到，也不能错误覆盖当前结果。

对应目标：G06。

## 9. E08｜大文件和长任务让用户知道进展

当井文件较大或某个 API 长时间运行时，用户能看到当前阶段、实际状态、已发生的异常和适当的下一步操作，不会因为界面长时间无反馈而误认为系统已经结束。

性能预估必须依据实测，不能直接复用某口井的历史运行时间来承诺其他井的处理耗时。若工具不支持当前数据规模，明确反馈限制，不宣称“任意大小均可处理”。

对应目标：G06。

## 10. E09｜区分业务视图与调试／评审视图

不要求第一版开发复杂双套前端，但需要**信息层次区分**。

| 使用者 | 首先需要看到的内容 |
|---|---|
| 测井业务用户 | 当前井、当前操作、阶段状态、关键结果、异常、可选择的下一步 |
| 开发／测试／评审人员 | 用户请求、系统选定业务动作、读取的关键上下文、Skill／Tool 调用记录、关键参数、真实 API 返回摘要、任务／版本关联、错误与耗时 |

Trace 的目标是识别实际问题发生在哪一层，**不是展示模型隐藏的完整内部思考过程**；所有专业结论仍应回溯到真实工具产物。

对应目标：G02、G06。

## 11. 五个端到端体验场景

| 场景 | 用户表达／事件 | 应有表现 | 不应出现 |
|---|---|---|---|
| U01 新井完整解释 | “帮我解释一下这口井”＋井资料 | 四阶段执行，展示各阶段结果和最终报告 | 只有“已完成”的空泛文字，无真实 Tool 证据 |
| U02 解释后查询 | “2035—2038 m 怎么样？” | 从正确版本查询实际层段结果 | 无条件从数据解编开始整井重算 |
| U03 修改并重解释 | “把这一层孔隙度改成 0.16，再解释” | 正确识别、受控预检、按实际依赖执行、保存历史 | 猜测修改粒度、编造专业依赖、直接覆盖原始资料 |
| U04 中途改变要求 | “先停一下，看看预处理结果” | 尽可能阻止后续步骤、显示已有效结果、区别外部任务真实状态 | 声称第三方 API 一定已经停止或错误采用迟到结果 |
| U05 第三方异常 | 智能处理超时或返回不完整 | 如实显示失败／未知状态，不使新结果误生效 | 将超时当成功、破坏上一有效版本 |

说明：U03 专业数值与重算范围的真实业务验收，需等待需求 Q01—Q04 确认；现在只能在 Mock 环境验证交互机制。

## 13. 当前不可承诺的效果

- 所有专业参数都允许修改；
- 任意自然语言要求都能不经确认自动执行；
- 所有第三方工具均支持真正的层段级计算；
- 智能体单独保证专业计算和地质结论正确；
- 所有大文件均可在统一固定时限内处理；
- 停止 Agent 等同于成功撤销外部 API 的计算；
- 在没有真实专业对照数据前承诺具体地质解释准确率。

## 1. 方案定位、依据与最重要的原则

本方案回答：在满足已讨论需求与预期效果的前提下，**哪些能力优先交给 AgentScope 配置，哪些必须复用或增加确定性业务代码**。不把未经实测的能力描述为现有成果，也不提前决定所有组件和代码结构。

依据：
- **会议要求**：围绕四阶段完成一口井解释；梳理真实／Mock 工具及其边界；优先研究 AgentScope 的 Agent、Prompt、Memory、Skill、Tool 等机制；先以最小验证工程测试动态选择、阶段交互、上下文及执行过程，再判断需要多少补充开发。
- **本轮已讨论方向**：采用交互式单井智能体；完整解释四阶段是业务主线，不是所有用户动作的硬编码固定 Workflow；保留既有持久化、业务校验和第三方 API 基础，不重造第二套业务事实源。

**最高设计原则：**

> **AgentScope 原生能力优先，配置验证在前，必要时补充最少代码。** 能通过 Prompt、Skill、Toolkit 及合适的原生机制完成的智能体行为，不预先做成自定义调度器；不能让大模型越过专业规则、真实工具和数据一致性约束。

配置优先不等于零代码；任何新增自定义调度代码都应有“原生能力验证记录、具体失败用例、无法满足的业务要求、最小修复范围”。

## 2. 业务边界与概念

### 2.1 用户的任务类型

- **完整解释**：以四个业务阶段组织完整单井解释；
- **只读操作**：查询当前井、层段、阶段结果、任务状态或比较结果；
- **变更操作**：对允许修改的对象提出修改，再根据已核实的依赖进行重解释；
- **报告操作**：按经确认的报告与结果版本规则生成／读取报告；
- **控制操作**：在允许的节点暂停、确认、继续或改变后续业务要求。

四阶段：**数据解编 → 数据预处理 → 智能处理 → 报告生成**。只读查询与版本比较不应为了表面流程一致而强制重走四阶段。是否支持任意中间阶段起步，取决于当前结果是否满足经确认的前置条件。

### 2.2 必须严格区分的四类对象

1. **自然语言上下文**：帮助 Agent 理解“这层”“刚才那版”，可以使用原生 Memory／Session；不得当成持久化业务权威事实。
2. **业务上下文**：当前用户、会话、井、任务、Active/View 结果版本及正在使用的层段等；从已授权、可验证的现有业务服务获取。
3. **专业数据与结果**：原始文件、解编资料、派生参数、第三方输出、阶段结果、报告及其来源和版本；由受控 Tool／API 与持久化服务维护。
4. **任务执行状态**：任务、阶段、底层 API 作业、等待确认、成功、失败或状态未知；不能只凭 Agent 的文字回答认定任务完成。

## 3. 候选总体架构：最小、可验证、可演进

```text
用户：自然语言＋授权井资料
           │
           ▼
AgentScope 主 Agent
- Prompt：身份、边界、不可伪造专业数据、调用工具原则
- 按需 Skill：专业任务操作说明与工具选用指导
- 原生 Toolkit：注册实际可用的业务工具
- 原生 Memory／Session：仅管理会话语言上下文
- 可选原生计划／中断／事件：必须先做版本适配验证
           │
           ▼
受控业务工具（按真实能力注册）
- 当前井／结果／阶段／版本查询
- 资料解编／预处理／智能处理／报告相关能力
- 参数修改预检／修改执行／影响分析／状态查询
- 结果比较、确认与继续等必要接口
           │
           ▼
已有业务服务＋第三方真实 API／Mock
- 参数合法性、授权和可修改范围
- 经核实的计算依赖与真实 API 调用
- 任务／阶段执行、版本、结果验收、异常及文件管理
- PostgreSQL／Redis／Artifact 存储等已建基础（以实际代码为准）
```

此图是**候选职责分配**，不是宣称项目已按此实现。第一步应盘点现有代码和项目中实际的 AgentScope 版本，复用已存在能力，避免平行建设状态服务、版本服务或第二套 Tool 注册体系。

**架构取舍**：不预先要求多 Agent；不把所有专业步骤藏进一个巨大“万能 Tool”；也不强行暴露真实 API 不具备的细粒度计算能力。Agent 能动态选择哪些 Tool，必须以真实接口和经过测试的 Mock 对应契约为准。

## 4. AgentScope 优先配置与验证矩阵

下表所列原生组件是**优先研究对象**；是否真正可用、如何组合及具体接口必须在项目锁定的 AgentScope 版本中验证。

| 所需能力 | 优先候选方案 | 需要验证什么 | 必须保留的硬约束 |
|---|---|---|---|
| 理解用户意图 | Agent＋System Prompt | 是否区分完整解释、查询、修改、比较、继续；能否拒绝越界操作 | 不用意图识别替代业务许可 |
| 工具发现与动态选择 | 原生 Toolkit＋清晰 Tool Description | 能否选对真实能力、正确传参、不漏前置步骤 | 工具自身强校验，未经授权不执行 |
| 专业过程说明 | Skills／Prompt | 是否正确读取、适用并根据结果调整工具调用 | Skill 文本不是强制数据一致性机制 |
| 连续交互 | 原生 Memory／Session／State | “这层”“上一版”是否能与查询结果正确对应 | 井、版本、层段执行时重新权威校验 |
| 多步骤任务变化 | Agent 原生能力；必要时比较原生 Plan | 动态插入查询／修改后能否调整后续工具调用 | 不把计划文本视作真实执行状态 |
| 暂停／确认／继续 | 当前版本可用的原生中断、交互、事件机制 | 用户确认点、恢复后状态及重复调用行为 | 第三方 API 是否真实停止需单独验证 |
| 过程展示与排错 | 原生事件流／Tracing＋已有日志 | 是否记录工具选择、参数、调用、状态与失败原因 | 原生 Trace 不可代替真实结果来源及业务审计 |
| 长任务管理 | 可用的 AgentScope 服务能力＋现有业务任务机制 | 断开、超时、恢复、状态查询 | 以持久化业务作业状态为执行事实 |

**默认不先引入**：多个专业子 Agent、复杂长期记忆、重型自定义编排器、第二套业务状态机、额外 Trace 平台。仅当测试证明现有原生及已有系统确实不能满足要求时再引入。

## 5. Prompt、Skill 和 Tool 的分工

### 5.1 Prompt：通用行为与边界

Prompt 说明当前 Agent 的角色与单井业务范围；优先调用业务工具获取事实；不得编造正式解释数值；缺少井、层段、版本或修改语义时先获取权威上下文或请求必要澄清；异常时如实报告状态。

**不要**把完整测井算法、变化频繁的 API 契约、授权规则和不可违反的版本逻辑写成只靠模型遵守的长 Prompt。

### 5.2 Skill：可复用的专业操作方法

先验证少量面向任务的 Skill，而不是因为有四阶段就必须建立四个 Agent 或大量 Skill，例如：
- 完整单井解释：四阶段的目标、前置条件、可用工具及阶段成果如何解释；
- 解释结果查询与比较：如何确定当前井、层段、View／Active 版本以及避免无关计算；
- 受控修改与重解释：先预检、获取权威依赖、调用实际工具、核对结果版本及来源；
- 报告操作：以经确认的解释结果版本为依据，按实际模板和可用工具生成。

拆分依据是**说明是否长且需要按任务选择加载**，不是机械的一业务步骤一 Skill。若简单 Prompt＋Tool Description 在第一轮已经稳定通过，就不强制引入 Skill；若 Skill 有实际收益再保留。

Skill 只解释怎么开展任务；是否允许修改、是否确实完成以及结果能否生效，仍由受控程序和 API 返回决定。

### 5.3 Tool：真实能力清单和诚实的接口映射

首先形成真实 API 与 Mock Tool 对照台账：工具名、业务用途、输入输出、依赖／前置条件、性能、错误及对应关系。

- 如果真实 API 有独立能力，可将其适当暴露给 Agent，验证动态选择。
- 如果真实 API 是文件交互的“一次返回多项结果”重 API，不能因为 Mock 拆分阶段表现，就声称真实服务具有多个独立细粒度 API。
- 如需要 Adapter 把重 API 的多个结果拆分成阶段成果用于展示，应保持**同一次实际调用**及结果来源可追溯，不能伪造多个真实调用事件。
- Tool 输入输出必须结构化且可校验；系统不能因为模型给出了一个数值就绕过业务验证。

Tool 暴露粒度由**真实 API 结构、Agent 选用准确性及可控性实测**决定，不能事先固定为“仅 5 个大型 Tool”或“直接开放所有 W01～W10”。

## 6. 四阶段的业务执行、交互和暂停

1. **完整解释路径**：Agent 识别完整解释，参考相应 Skill，基于合法输入及现有结果依次开展数据解编、数据预处理、智能处理及报告操作；经业务前置条件许可后进入下一阶段。
2. **非完整任务**：查询、比较、状态查询可直接获取已有成果；修改先预检并依业务规则选择必要的后续处理；不做无意义的四阶段回放。
3. **阶段确认**：配置候选的暂停／继续机制并进行 Mock 验证。哪些阶段强制停尚未由业务确认，不能写成所有任务必须四次停顿。
4. **任务中途变更**：Agent 可调整后续意图及工具选择，但已提交第三方的重 API 可能无法物理取消。必须将旧任务与原输入版本绑定，迟到结果不得无条件覆盖新的 Active 结果。

本节描述期望的职责边界；如仅靠 AgentScope 原生机制不能可靠遵循强制前置条件，才针对具体失败用例补充最小确定性校验或调度代码。

## 7. 修改、真实依赖及局部重解释

**示意交互（非专业规则承诺）：** 用户要求把“当前井的 2035–2038m 孔隙度改成 0.16，再解释”。

按以下方式划分职责：

1. Agent：解释用户意图、解析候选井／层段／参数／值，选择合适 Tool。
2. 受控 Tool／业务服务：核实当前授权井、基础结果版本、目标对象和修改粒度，判断该修改是否允许。
3. 受控影响分析：读取由专业人员及实际算法／接口确认的参数—结果依赖，返回明确的失效及必需计算范围；未知时不得臆断。
4. Agent：根据受控影响分析返回的**可用能力与必要步骤**选择后续 Tool；强制依赖仍由业务程序保障。
5. 真实／Mock API：实际执行可支持的计算；校验结果及其来源、输入版本、工具／模型版本，生成新结果。
6. 版本服务：结果完整且有效时才允许新版本按规则生效；失败、不完整或晚到结果不得破坏旧有效结果。

### 两种“局部”必须区分

- **业务结果局部更新**：受影响范围由真实业务依赖决定，不受影响结果不被错误覆盖；
- **计算执行局部化**：第三方真实 API 是否只算指定井段，必须有接口说明和实际证据。若只能整井计算，应明确标注实际整井计算，不假装发生层段级计算。

关于“孔隙度=0.16”是层平均值、采样点覆盖还是其他业务修改，现阶段未确认。此类专业语义不在 Prompt 中凭经验猜测。

## 8. 状态、版本、文件及异常边界

### 8.1 状态职责

- 原生 AgentScope Memory／Session 用于对话语义，必要时关联已有业务上下文；
- 现有持久化业务系统（以当前仓库实际实现核实）管理当前井、Active/View 结果版本、历史版本、任务执行、阶段成果与文件来源；
- 已有上下文服务若可满足要求，直接复用，不新增平行的第二套 Context 存储；
- 任何修改或重解释请求执行前，应重新校验业务状态，而不是仅信任模型记忆。

### 8.2 结果生效

优先复用已有版本与任务机制。参考原则：旧有效版本保持不变；新计算结果先处于未生效状态；完整性、授权和版本冲突检查通过后，再按业务规则升级；失败或迟到的旧任务不能抢占当前结果。

跨远程 API／文件存储／数据库不能预设有同一个全局事务。外部超时可能代表**状态未知**而不是确定失败；重试须结合实际接口状态查询与幂等支持。

### 8.3 大文件与专业事实来源

原始资料不得经无必要的超长上下文或聊天消息持久化通道传递。优先复用当前项目已经核实的上传／Artifact 机制，仅将受控文件标识和小型必要参数传给工具。专业数值、计算派生结果和报告均保留真实来源与版本；模型文字回答不成为新的原始数据。

### 8.4 Trace 与展示

业务界面展示“当前井、阶段、成果、状态、异常、后续动作”。调试界面或日志记录动作选择、Tool 名、结构化参数摘要、任务与执行 ID、API 调用、结果及版本。不以模型完整隐藏推理作为项目验收要求。

## 9. 先独立验证，再选择性集成

### P0：盘点而不是重构

检查当前仓库的实际 AgentScope 版本、Prompt／Agent／Tool 注册、四阶段代码、已有 Context／Version／Task／Execution、Artifact 上传和真实 API 接口。形成可复用组件与真实能力台账。本阶段不改主业务代码，不预设现有模块必须被替换。

### P1：最小 Mock 配置验证

独立构建一个小型工程，优先配置一个主 Agent、基础 Prompt、必要 Skill 和少量与真实工具对应的 Mock。逐项完成《05 测试与验收方案》的 A01～A06、A08；原生 Plan 作为必要时的对照，不强制引入。

重点测试：不同语句选择不同工具、四阶段可解释、阶段确认、跨轮上下文、修改预检、用户中途改变要求以及工具出错反馈。

### P2：记录原生边界与最小代码缺口

未通过用例必须有复现条件、相关 Prompt／Skill／工具契约、尝试过的原生能力、失败证据，以及为何需要增加确定性程序。对业务安全硬规则不做“Prompt 代替代码”的无效尝试。

### P3：选择性接入现有项目

保留能复用的业务服务与文件／版本基础；根据 P1／P2 证据替换或调整真正有必要的 Agent 层代码；真实业务 API 验证《05》的 B01～B08 和安全用例。阶段测试通过不等于所有生产场景通过。

## 10. 当前技术决策及待验证表

| 项目 | 当前结论 | 依据及剩余限制 |
|---|---|---|
| 总体路线 | **AgentScope 原生优先，先配置后补代码** | 本轮明确决策；需通过最小工程验证 |
| Agent 数量 | 第一轮先用一个主 Agent | 控制变量的实施建议；未来可按证据扩展 |
| 四阶段 | 完整解释的业务主线，不是所有操作的固定总工作流 | 已讨论共识 |
| Prompt／Skill | 优先承载行为规范和专业操作方法 | 具体拆分及 Skill 效益待对照测试 |
| Toolkit | 以真实能力台账注册并验证调用粒度 | 重 API 与 Mock 拆分映射仍需确认 |
| Memory／State | 原生机制用于对话；业务权威事实从已有持久化系统获取 | 具体版本接口和会话恢复需实测 |
| Plan／复杂多 Agent | 不预先强制采用 | 仅在对应场景证明需要时添加 |
| 修改依赖 | **不能凭示意图写死** | 待专业算法、第三方接口及业务方确认 |
| 层段计算 | 不承诺真实物理局部计算 | 待第三方接口实测 |
| 安全与版本 | 复用必要确定性业务约束 | 不能仅以 Prompt／Skill 保证 |
| 性能指标 | 先采集真实基线后确定 | 不虚设大文件能力和执行时长 |

## 11. 方案验证和定稿条件

技术方案只有在下列条件成立后才能由讨论稿转为受证据支持的正式实施方案：

1. 实际 AgentScope 版本和可用原生机制已盘点，并完成最小配置验证；
2. 不同业务动作的工具选择、四阶段交互、上下文和中途任务调整有可复现的测试证据；
3. 真实／Mock 工具清单及其能力差异被确认；
4. 不可由原生能力满足的部分有明确失败案例与最小代码补充决策；
5. 重要专业依赖及第三方局部计算限制被标注为已确认或待确认，不存在凭空承诺；
6. 真实业务、异常、版本保护和大文件性能按《05 测试与验收方案》执行。

**本方案的成功标志不是“使用了多少 AgentScope 组件”，而是证明确实优先使用了适用的原生机制，同时保留测井业务必须具备的确定性保障。**

## 13. Task 013：最终回复 Response Evidence Contract

Task 013 落实 Task 012E 的回复 Grounding 决策：Application / Tool 结果先形成不可变 `ResponseEvidenceEnvelope`，再由服务端确定性 renderer 生成业务核心正文。合同绑定 task、execution、已解析 scope、InputVersion/revision、operation、回复门控状态、真实 `ExecutionStatus`、来源类型和 evidence refs；它不取代 OperationPlan，也不新增业务执行状态机。

`SUCCESS`（成功）须具有匹配 Task / Execution 引用；`REPORT_READ`（读取报告）及 `REPORT_GENERATION`（生成报告）另须报告引用。`QUEUED`（排队等待）、`RUNNING`（正在执行）、`NEED_CLARIFICATION`（需要澄清）、`UNSUPPORTED`（当前不支持）、`REJECTED`（请求拒绝）、`FAILED`（执行失败）不能渲染成业务成功。Fixture / Mock 回复正文必须注明“非真实业务结果”；来源未知应明确说未核验。

Agent 可以在未来补充不改变合同事实的解释性语言；Task 013 当前不启用模型来渲染关键业务事实。报告只展示指定 Execution 持久报告，阶段确认和后续阶段完成分开陈述。此项首批覆盖 AgentScope 聊天 Tool、上传与执行流；Read API / Panel DTO 的统一 envelope 接入仍待后续 Task。

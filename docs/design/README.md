# docs/design｜项目主设计基线

本目录回答五个连续问题：

1. **需求**：我们需要做什么；
2. **目标**：本次建设要达到什么程度；
3. **效果**：用户实际应该看到什么行为；
4. **方案**：当前证据支持什么实现方式；
5. **测试**：如何证明方案达到了效果且没有破坏业务安全。

## 治理状态

| 文件 | 治理状态 | 修改原则 |
|---|---|---|
| 01 需求规格说明 | BASELINE | 业务需求变化时修订 |
| 02 建设目标 | BASELINE | 建设目标变化时修订 |
| 03 预期效果 | BASELINE | 用户效果目标变化时修订 |
| 04 技术方案 | VALIDATING | 依据 docs/evidence 与测试证据修订 |
| 05 测试与验收 | VALIDATING | 依据新风险、新证据和验收缺口修订 |

## 重要规则

- 01～03 不因为某次技术实验成功或失败而自动改变。
- 04～05 可以随实验证据迭代，但必须说明依据。
- Mock 能力不得写成真实公司 API 已具备能力。
- 实验通过不得自动解释为可以删除现有确定性安全代码。
- 权限、版本、一致性、专业计算、真实依赖、幂等及外部 API 状态必须由确定性代码或真实业务契约保障。

如本目录与旧的 Current Implementation 文档描述不同：

> **docs/design 定义目标与当前认可的设计方向；旧文档描述现有实现。**

不得因为现有代码暂时不同，就反向修改需求、目标和预期效果。

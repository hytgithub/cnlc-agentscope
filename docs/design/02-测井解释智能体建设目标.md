# 02｜测井解释智能体建设目标（讨论稿）

> 版本：v0.1  
> 日期：2026-09-30  
> 状态：目标方向已讨论；量化指标和真实业务覆盖度待评审  
> 对应文件：[01 需求规格说明](./01-测井解释智能体需求规格说明.md)、[03 预期效果](./03-测井解释智能体预期效果.md)、[04 技术方案](./04-测井解释智能体技术方案.md)、[05 测试与验收](./05-测井解释智能体测试与验收方案.md)

## 1. 文档定位与依据

本文件回答“**本次建设要达到什么程度，什么才算成功**”，不展开具体代码结构。

依据分为两部分：

1. **会议方向**：2026-09-29 会议讨论明确四阶段业务主线，要求优先研究和使用 AgentScope 的 Agent、Prompt、Memory、Skill、Tool 等机制，先用 Mock 进行最小验证，验证自然语言、阶段交互、局部重跑与上下文，再针对确需解决的问题补充代码。
2. **本轮设计讨论形成的目标**：以单井为中心持续交互，支持完整解释以外的查询、受控修改、结果比较和版本回溯；将专业数据和版本正确性作为明确的硬约束。

**目标不等于成果。** 本文定义期望达到的状态；除有独立测试证据外，不宣称目标已实现或通过验收。

## 2. 建设总目标

建设一个面向**单井常规测井解释**的交互式智能体：用户通过自然语言发起完整解释，也可以围绕已有解释结果持续查询、受控修改、重新解释、比较和生成报告；智能体结合当前业务上下文动态组织操作，借助真实受控 Tool／API 获得专业结果，并保障操作可追溯、结果有来源、失败不破坏已有有效结果。

本次技术建设遵循：

> **优先利用 AgentScope 原生能力及可配置的 Prompt、Skill、Tool 等机制；先通过独立 Mock 验证工程确定能力边界，再选择性集成现有项目。只有已证实无法由框架解决，或者必须确定性保障的专业规则、授权和数据一致性，才补充必要业务代码。**

这是**实施方法约束**，而不是“零代码”承诺。

## 3. 六项核心建设目标

### G01｜自然语言驱动业务操作

用户表达不同意图时，Agent 应结合当前任务及井上下文选择相应操作，不是统一进入固定四阶段 Workflow。

覆盖的动作至少包括：完整解释、结果查询、受控修改、重解释、比较及必要的阶段交互。

**达到目标的表现**：同一口井的不同请求触发正确的业务能力与 Tool；只读请求不发生不必要的写入或整井重算；意图有歧义时不执行高风险操作。

关联需求：R02、R03、R06、R07。

### G02｜完成单井真实解释闭环

能够针对至少一口经授权的脱敏测试井，调用真实业务工具组织数据解编、数据预处理、智能处理及报告生成，取得可追溯的阶段结果和正式产物。

**达到目标的表现**：不是仅有界面演示或 Mock 返回；实际调用的业务 API、输入资料、输出数据、执行状态与结果来源可以核查。

**边界**：专业解释的准确程度依赖经确认的测井标准和参考结果；真实井闭环完成不自动等同于所有专业结论已准确。

关联需求：R01、R09、R10、R12。

### G03｜解释完成后仍支持持续交互

完整解释仅是可执行的业务任务之一；结束后用户能够基于已有井和结果继续查询、比较、修改、重解释与报告操作，而非每次重新上传或从首阶段执行。

**达到目标的表现**：“这层”“刚才那版”等上下文引用在明确情况下能够正确解析；涉及井、版本等权威信息时以业务系统校验为准。

关联需求：R03、R06、R08。

### G04｜受控修改与历史结果保护

自然语言用于表达修改意图，但不赋予大模型直接篡改正式测井数据的权限。修改必须落到经过验证的操作对象、参数规则及受控工具。

**达到目标的表现**：修改范围明确、参数校验通过后才发生写入；旧有效结果和修改记录保留；不明确或非法的修改不会生效。

关联需求：R04、R08、R09、R11。

### G05｜按真实业务影响范围重解释

修改后识别受影响的业务结果并执行所需计算，避免遗漏必需重算，也避免把任何修改一律解释为全流程从头执行。

**达到目标的表现**：受影响结果和未受影响结果的处理符合经确认的依赖规则；报告与对应结果版本一致。

**关键限定**：业务结果的局部更新与底层 API 的物理局部计算是两个目标。前者属于核心业务目标；后者取决于第三方接口实测，不能提前许诺。

关联需求：R04、R05、R08、R09。

### G06｜可靠执行、透明反馈和结果可信

能客观反馈当前任务、阶段及工具状态。超时、异常、无完整数据、任务冲突和迟到结果不得把旧的有效解释结果破坏或使半成品生效。

**达到目标的表现**：错误和结果来源可追踪；有效版本与失败版本区分清楚；大文件与长任务以实际数据和工具限制为依据反馈，不编造执行进度或耗时。

关联需求：R11、R12、R13。

## 4. 两层建设目标：先证明机制，再证明业务

### 4.1 第一层：最小 AgentScope 配置验证

采用相对独立的最小工程，尽量只使用 AgentScope 原生 Agent、Prompt、Skill、Toolkit、上下文和 Mock Tool。

重点证明：

- 能把不同自然语言操作映射到适当的 Tool；
- 能按四阶段完成演示井解释，按配置暂停、确认并继续；
- 能在完整解释后查询已有结果；
- 能理解示例修改、触发受控预检及计划必要的重解释动作；
- 能连续理解当前井／层段／版本的对话引用；
- 能记录并检查实际工具调用轨迹。

**退出产物**：框架能力验证结果、最小配置、用例执行记录及需要补代码的证据清单。第一层**不宣称**测井专业准确性已经验证。

### 4.2 第二层：集成当前项目的真实业务验证

将已验证的配置方案选择性集成现有项目，复用已有 Tool、API 适配、任务、版本和存储能力。

重点证明：

- 至少一口脱敏测试井的真实完整解释；
- 已确认参数和层段规则下的受控修改与正确结果更新；
- 真实版本、报告和执行轨迹正确关联；
- 外部 API 异常、长任务及重复／冲突操作不会污染有效结果；
- 性能及文件规模边界通过真实测量得到。

**退出产物**：真实业务对照结果、异常及性能记录、实际受限能力与验收结论。

## 5. 当前必须优先达到的五个场景

| 场景 | 用户操作 | 预期达到的目标 | 第一层／第二层界限 |
|---|---|---|---|
| C01 | 帮我解释这口井 | G01、G02 | Mock 验证完整调度；真实 API 验证专业闭环 |
| C02 | 2035—2038 m 怎么样 | G01、G03 | 先验证查询工具选择，再核对实际结果来源 |
| C03 | 修改指定层段参数 | G03、G04 | 先验证识别与预检；真实修改须依赖明确业务规则 |
| C04 | 按修改重解释 | G04、G05 | 先验证动态调度；真实计算依赖和范围必须另行核实 |
| C05 | 第三方计算失败／超时 | G06 | Mock 注入异常；真实集成验证结果版本不被污染 |

此表描述**验收场景方向**；专业数据、工具能力、报告规则等尚不确定时，不得以示例 Mock 结果替代实际业务结论。

## 6. 明确的非目标

为避免范围无边界扩大，以下**不作为本次达标的前置要求**：

- 多井、区块级联合解释或成像测井；
- 强制采用多 Agent、长期记忆或独立复杂规划平台；
- 支持任意参数的任意修改；
- 宣称所有第三方 API 都支持物理层段计算；
- 在缺少基线测试前承诺具体成功率、固定秒级耗时或最大文件规模；
- 建成正式生产级前端、完整运维平台或与核心业务无关的通用聊天能力。

若后续业务确需上述能力，应形成新增需求及独立验收标准。

## 7. 目标完成判定与量化指标

### 7.1 本轮可以明确的判定原则

1. 关键交互场景能复现正确 Tool 选择与参数，而非仅根据 Agent 的文字回答判定成功；
2. 真实井闭环确实调用真实业务接口并产生可核查结果；
3. 修改与重解释遵守实际专业规则，旧有效结果不被静默覆盖；
4. 关键故障情况下不出现越权修改、半成品误生效或历史版本污染；
5. 新增自定义代码应有对应的原生能力验证记录或确定性业务安全理由。

### 7.2 暂不编造的指标

自然语言识别准确率、真实计算准确度、平均耗时、工具超时阈值和最大可处理文件规模，须在数据集、专业参考答案及 API 实测结果具备后制定。

对应测试编号、证据结构和退出条件见 [05｜测试与验收方案](./05-测井解释智能体测试与验收方案.md)。

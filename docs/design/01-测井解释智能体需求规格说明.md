# 01｜测井解释智能体需求规格说明（初稿）

> 版本：v0.1  
> 日期：2026-09-30  
> 状态：需求基线初稿；部分业务规则待确认  
> 适用范围：单井常规测井解释  
> 文档定位：回答“需要做什么”，不预先规定 AgentScope 实现方式。

## 1. 目的和需求来源

本文件建立单井测井解释智能体的初始需求基线，为《02 建设目标》《03 预期效果》《04 技术方案》《05 测试与验收方案》提供可追溯的输入。

需求依据分层：
- **会议提出**：2026-09-29 会议逐字稿《文字转写_HL招标智能体_605628391.docx》及《2026-09-29会议纪要总结.docx》，涉及四阶段、Mock/真实 Tool、自然语言修改、阶段确认、上下文、Trace、大文件与配置优先的建设方向。
- **后续讨论确定的建设方向**：采用围绕当前井持续工作的交互式智能体；完整解释是其支持的任务之一，不能将所有操作硬编码为只能执行四阶段的固定流程。
- **设计推导／建议**：查询后的持续交互、版本比较、数据安全等细化条目；需要实施及业务评审，不冒充会议原文。
- **未知项**：明确标记为待业务确认或待接口实测；不得在开发中自行假设。

本文“已纳入基线”表示当前设计讨论认可该需求方向，**不表示业务规则细节全部确认，也不表示代码已经实现或通过验收**。

## 2. 产品范围与基本约束

### 2.1 核心范围

面向一口井的常规测井解释，支持以自然语言和井资料发起完整解释，并围绕已有解释结果继续操作：查询、受控修改、重解释、比较和报告生成。

完整解释的四阶段业务主线是：

1. 数据解编；
2. 数据预处理；
3. 智能处理；
4. 报告生成。

四阶段用于组织完整解释任务及展示业务进度，**不等于所有用户操作必须按四阶段重新执行**。

### 2.2 暂不纳入本轮核心范围

多井联合／区块级解释、成像测井、复杂多 Agent 协同、与单井解释无关的开放领域问答；今后如需纳入，应新建需求并调整验收范围。

### 2.3 通用业务约束

- 原始井资料及已生效的历史解释结果不可因后续自然语言操作而被静默覆盖。
- 大模型可以理解意图、选择适当操作并解释结果，**不得自行编造专业数值并当作正式计算结果**。
- 实际专业计算、修改合法性、权限、版本状态和结果生效应以真实业务数据、受控 Tool 与经过验证的规则为依据。
- 第三方真实 API 是外部约束；不得把 Mock Tool 模拟出的原子能力视为真实 API 已具备的能力。

## 3. 功能需求基线

下面按 R01—R13 编号；“来源”用于区分会议方向与本轮设计细化，后续评审可补充会议原文定位和业务签字。

| 编号 | 需求 | 最低可观察行为 | 来源／状态 |
|---|---|---|---|
| R01 | 单井完整解释 | 用户提交井资料并提出完整解释，系统组织四阶段并形成解释结果和报告 | 会议明确方向；已纳入基线 |
| R02 | 自然语言业务操作 | 理解完整解释、查询、修改、重解释、比较等不同业务要求 | 会议提出自然语言验证＋后续讨论扩展；已纳入基线 |
| R03 | 已有结果查询 | 正确读取当前井、层段及版本的数据，不无条件整井重算 | 后续讨论细化；已纳入基线 |
| R04 | 受控参数／结果修改 | 解析修改意图，校验对象与权限，保存变更且不覆盖原始资料 | 会议给出修改孔隙度示例；细则待确认 |
| R05 | 按实际影响范围重解释 | 根据真实业务依赖处理失效结果；不默认全部重算，也不遗漏必需重算 | 会议提出局部重跑；实际依赖与 API 能力待确认 |
| R06 | 连续上下文 | 连续理解“这层”“刚才版本”等表达；实际井／版本以权威业务状态为准 | 会议提出当前井、阶段、修改与版本上下文；已纳入基线 |
| R07 | 阶段控制 | 完整解释中显示阶段结果，按约定支持暂停／确认／继续 | 会议明确提出；强制确认范围待定 |
| R08 | 历史可追溯 | 修改前后结果、来源、范围及操作记录可查；支持明确版本比较 | 会议讨论回溯＋后续细化；已纳入基线 |
| R09 | 真实业务 Tool 执行 | 数据获取和专业计算来自受控工具，模型不能把猜测值写成正式结果 | 会议关于 Tool 选择和真实 API 的要求＋设计约束 |
| R10 | 真实／Mock Tool | 可用 Mock 验证交互和调度，真实 API 验证专业结果；两者有清晰契约映射 | 会议明确；已纳入基线 |
| R11 | 外部失败与结果安全 | 调用超时、失败、结果缺失时不把不完整新结果生效，不破坏旧有效结果 | 会议提出异常边界＋后续安全要求 |
| R12 | 过程可观察 | 记录业务动作、调用工具、关键参数、状态、结果及错误，提供适当展示 | 会议明确 Trace／Debug 需求 |
| R13 | 大文件和长任务感知 | 识别规模及工具限制，显示实际进度、耗时或异常，不能承诺未经验证的性能 | 会议明确大文件与性能风险 |

### 3.1 典型自然语言场景

以下深度、数值和井名均为**交互示例，不是已核实的井数据或业务计算结果**：

- 完整解释：“帮我解释一下这口井。”
- 查询：“看看 2035–2038 m 这一层。”
- 修改：“把刚才这层的孔隙度改成 0.16。”
- 重解释：“按刚才修改的参数重新解释。”
- 比较：“比较修改前后的结果。”
- 阶段控制：“先停一下，我要看预处理结果。”

任何具有修改副作用的操作，在操作对象或参数含义不明确时均应阻止写入，而不是根据对话猜测目标。

## 4. 待细化需求

| 编号 | 当前明确的能力方向 | 尚未确定的细则 |

## 5. 六个开放问题

这些问题在当前阶段**不强制给出假答案**；但在相关业务功能进入真实验收前必须解决。

| 问题 | 尚需明确的内容 | 推荐确认方式 |
|---|---|---|
| Q01 可修改范围 | POR、PERM、SW、Rw、层段边界、采样间隔、模型选择等哪些允许修改 | 测井业务人员给出允许修改清单及规则 |
| Q02 修改粒度 | “某层孔隙度＝0.16”表示层平均值、全层采样点还是修正参数 | 业务操作定义＋测试样例 |
| Q03 计算依赖 | 参数修改后哪些结果失效，是否涉及跨层段／整井依赖 | 真实算法／第三方契约及专家核对 |
| Q04 API 范围 | 第三方 API 是否支持指定深度范围执行及最小执行粒度 | API 文档及实际调用 |
| Q05 人工确认 | 哪些阶段、修改和版本操作必须用户确认 | 产品／业务规则评审 |
| Q06 报告定位 | 随时生成或仅完整解释末尾生成、是否单独版本化 | 报告使用场景与业务方确认 |

对 Q04 必须严格区分：**用户只更新某层段的业务结果**不代表**底层 API 只计算某层段**。

## 6. 必须以实测明确的事项

| 编号 | 验证事项 | 证据形式 |

## 7. 需求优先级与阶段边界（建议，待正式批准）

**核心验证**：R01、R02、R06、R07、R09、R10、R12 的 AgentScope 配置可行性；并以 Mock 用例覆盖 R03～R05 的交互机制。

**真实业务验证**：以真实 API 核实 R01、R04、R05、R08、R11、R13；所有专业数值与依赖必须有正式业务依据。

**后续扩展**：增加更多可修改专业参数、改进多井能力或复杂 Agent 协作须以新增需求和专项评审决定。

此优先级是本轮设计建议，不宣称已通过管理或业务方审批。

## 9. 需求基线完成判定

第一阶段完成不要求 Q01—Q06 立即回答。完成标准是：

1. 已纳入基线的需求具有清晰的可观察行为及来源类别；
2. 所有不确定的专业含义、接口能力与交互规则明确列为待确认；
3. 不使用模型推测或 Mock 表现代替真实测井依据；
4. 建设目标、预期效果、技术方案和测试均可追溯到本文件；
5. 新信息出现后，通过版本化修订本文件，而不是悄然改变开发假设。

# Task 012C.1｜写范围语义与安全边界核对

> 日期：2026-10-04
> 分支：`codex/task-12-agentscope-native-capability-poc`
> 状态：已实施；验证结果与未解决项见本文
> 决策：结论 B——只允许继承与同一 Task / Execution 工作基线相匹配的 Active scope；无本轮明确范围且无此类 Active scope 时必须澄清。

## 1. 范围与证据边界

本核对检查了需求 `docs/design/01`、效果 `docs/design/03`、技术方案 `docs/design/04`、验收方案 `docs/design/05`，以及交互文档、Operation Parser / Resolver / Bridge / Capability / Validator / State / Adapter 和相关测试。设计 04/05 明确禁止模型自行补全缺失写范围；需求和产品材料没有证明四个参数天然只能作用于整井。因此，现有 `WHOLE_WELL` capability 只说明当前 handler 支持什么，不构成用户未指定时默认整井的依据。

本次不判断孔隙度、渗透率、采样间隔或预测模型在专业业务上应有哪些局部粒度；缺少业务资料的参数语义标为 `BUSINESS_CONFIRMATION_REQUIRED（需要业务确认）`。本次改变的是“未说明范围时是否可写”的通用安全边界，不增加专业规则。

## 3. 场景决策表与结果

| 场景 | 旧行为 | 目标行为 | 一致性 / 实施结果 |
|---|---|---|---|
| S01 明确“全井” | 候选整井进入 capability / handler | 本轮有明确整井措辞即可使用 `WHOLE_WELL（整井）` | 一致。结构化解析和集成路径覆盖明确整井；Middleware 检查该范围确由本轮文字支持 |
| S02 无范围、无 Active scope | Bridge 将缺失 scope 合成为整井 | `NEED_CLARIFICATION（需要澄清）`，不提交 Execution | 不一致已修复。Resolver 产生缺 scope issue，Bridge 不再合成全井 |
| S02 无范围、同版本 Active 整井 | 可继承或被默认值掩盖 | 允许继承 | 允许；仅当 Active 的 `base_execution_id` 与本次解析出的 execution 相同 |
| S02 Active 为局部范围 | capability 不支持局部，存在被默认值扩大风险 | 不扩大；由既有 scope 校验返回不支持 / 澄清 | 已覆盖：不会变成整井 |
| S02 只有 View scope | 读焦点可能与写路径混淆 | View 不得赋予写范围 | 已覆盖：缺 scope 仍澄清 |
| S03 明确局部范围 | capability 仅支持整井 | 稳定拒绝，不提升整井 | 已覆盖，相关 Resolver / Bridge 测试断言不创建执行 |
| S04 采样间隔缺范围 | 默认可能按整井继续 | 没有可信 scope 时澄清 | 已覆盖；参数的“天然整井”语义仍待业务确认 |
| S05 预测模型缺范围 | 默认可能按整井继续 | 没有可信 scope 时澄清 | 已覆盖；模型的“天然整井”语义仍待业务确认 |
| S06 先查看局部范围再无范围修改 | View 可能影响写焦点 | View 只帮助理解，不得成为写授权 | Resolver 单测覆盖 View-only 无继承；无 scope 的修改澄清 |
| S07 旧 View / 新 Active | 旧查看引用可能串入写计划 | Active 当前工作基线优先且仅同版本范围可继承 | 已覆盖旧 View 不覆盖当前 Active；Execution 冲突仍要求显式解决 |

`S01–S07` 的直接结果主要来自结构化单元测试和工具入口集成测试；它们验证确定性代码边界，不是自然语言模型准确率评测，也没有真实 PostgreSQL / Redis 环境写入。

**Write Safety 独立结论：**本次边界回归没有观察到无范围写入或范围升级后创建 Execution；缺 scope 及模型虚构整井范围均被阻断。压缩会话用例有 1 次因摘要中的旧井引用而被 Bridge 拒绝，属于可用性 / Authority 路由失败，不是 Write Safety 越权；但该失败仍独立保留，不由通过率掩盖。

## 4. 决策与实现

选择结论 B。代码在 `OperationContextResolver` 对无 scope 的 `MODIFY_PARAMETER` 记录澄清问题；仅同 Task、同一显式 execution 的 Active scope 可继承。View 不参与写 scope 继承。`OperationExecutionBridge` 不再为缺失参数 scope 合成 `WholeWellScope`；对 Task/Execution 事实解析后仍缺范围时返回澄清。AgentScope Middleware 会拒绝没有本轮文字锚定的模型 `WHOLE_WELL` 候选范围，避免 Agent 绕过语义澄清直接提交。

显式局部范围仍按当前 capability 规则拒绝，不会以全井代替。多操作计划只要有未解决的 scope issue 就不会部分执行。Prompt 仅同步告知约束；安全由 Resolver / Bridge / Middleware 确定性实现。

## 5. 架构问题与运行中发现

**Architecture Issue：**在强制 AgentScope 上下文压缩的集成用例中，模型请求只收到框架生成的 `<system-info>` 摘要作为最近 user-role 内容，其中含可信会话 Task 的井号但没有当前原始用户轮次文本；Mock 模型据此形成 WELL_ID 引用，Bridge 安全拒绝 `SESSION_WELL_NOT_FOUND`，没有产生写副作用。此行为不会放宽范围边界，但说明压缩后“对话摘要用于理解”与“本轮实体引用用于 Authority”需要更明确的调用契约。建议单独记录并审查当前 Interaction Middleware 向模型传递当前输入的方式；本 Task 未以摘要作为 Task / Execution / Scope 授权，也未扩大修改范围处理此问题。

这项失败与 Write Safety 结果分开报告：**本轮写请求被拒绝，没有创建 Execution；未观察到写安全越权。** 但现有测试 `test_mock_shell_supports_context_compression_and_keeps_task_identity` 仍未通过，故完整集成测试不能宣称全绿。
